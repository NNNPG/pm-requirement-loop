# pm-requirement-loop：需求分析 Loop 与单一设计文档生成

输入一段产品需求，产出一份结构完整、逻辑连贯、可直接交给研发的设计文档——中间自动完成需求澄清、方案设计、独立反方评审、问题修正和质量检查。

**快速开始**：在对话中输入以「需求：」开头的描述，或直接粘贴需求材料并说「帮我拆一下这个需求」即可触发，无需固定表单。

---

## 1. Skill 简介

这是一套面向真实业务项目的需求分析与设计方法。你提供初始需求和项目资料，它负责完成从需求理解、歧义收敛、方案设计、反方评审、问题修正到最终文档交付的完整过程。

**它和「一次性生成设计文档」的区别**：一次性生成只产出初稿，方案中的逻辑矛盾、流程缺口、异常场景遗漏都会原样留在文档里。本 Skill 在初稿（方案基线）建立后，会主动切换到评审者视角对当前方案挑毛病——每条评审意见必须给出可验证的依据和影响分析，经裁决后只定向修正受影响的部分，并检查修正没有引入新矛盾，最后才整合成最终文档。

一个关键设计：多轮分析过程本身不是交付物。你最终拿到的只有**一份**从当前有效方案重新编排的完整文档，而不是各轮讨论记录的拼接。

## 2. 适用场景

**适合**：

- 将业务需求 / 产品构想转化为可评审的产品设计方案
- 对复杂功能进行模块化拆解（板块 → 可独立开发验收的功能点）
- 梳理端到端业务流程、系统交互与上下游数据流转
- 明确功能规则、输入输出、依赖关系和异常处理
- 通过多轮评审完善已有方案（可基于现有方案继续迭代）
- 生成面向研发、测试和交付团队的设计文档（含验收标准）

**不适合**：

- 简单文本任务：润色、翻译、写简短说明
- 已经定稿、只需排版美化的文档
- 单点小问题的快速问答（走完整流程反而低效）
- 纯技术实现任务（写代码、调试）——本 Skill 止步于设计文档

## 3. 核心能力

以下能力均由 Skill 规则文件实际承载：

- **需求理解与歧义识别**：区分「表面诉求 / 底层目标 / 成功判据」三层；只识别会导致不同方案或验收结果的实质性歧义，能靠低风险假设推进的不阻塞
- **方案设计与模块拆解**：8 维度分析框架（含数据流转、系统衔接等交付视角）；板块职责划分与功能点拆解，粒度为「一个开发能独立接手」
- **多轮反方评审与裁决**：12 个评审维度；每条意见必须带成立依据、影响分析和严重程度，裁决为接受 / 拒绝 / 待确认
- **方案基线维护**：全程唯一 Design Baseline，每轮只做定向修正 + 回归检查，不重写整个方案
- **信息可信度管理**：全文严格区分五类信息——已确认事实 / 设计假设 / 设计建议 / 未决问题 / 已否决方案
- **需求-设计-验收追溯**：每个需求可追溯到决策 → 板块 → 功能点 → 验收用例（R→D→M→F→AC）
- **单一文档生成**：固定 10 章结构，可脱离对话独立阅读

## 4. 工作流程

```text
需求输入
  → ① 需求理解与澄清（还原真实问题，登记待确认问题）
  → ② 总体方案设计（8 维度分析 + 关键决策记录）
  → ③ 模块与功能点拆解（建立唯一方案基线）
  → ④ 反方评审（12 维度找实质缺陷）
  → ⑤ 问题裁决与定向修正
  → ⑥ 一致性与回归检查
  → ⑦ 收敛判断 ──未收敛且未达轮次上限──→ 回到 ④
  → ⑧ 最终设计文档生成（通过质量门禁后交付）
```

说明：

- ①~③ 首次执行一遍，产出方案基线 v1；④~⑦ 循环执行，**最多 5 轮**实质性评审与修正。
- 收敛需同时满足十项条件（目标范围明确、流程闭环、无未处理的重大缺陷、可追溯等）。
- **达到 5 轮上限不等于方案自动通过**：此时交付的是「带限制交付」版本，会明确列出未解决的重大问题、影响范围，以及哪些部分可继续开发、哪些必须等待确认。
- 生成最终文档前执行质量门禁（需求覆盖、逻辑、一致性、可执行性等检查）；发现重大问题会退回修正，而不是硬交一份看似完整的文档。

## 5. 如何使用

自然语言输入即可，以下示例可直接复制使用（把需求内容换成你的）。

**从零开始——生成完整设计文档**：

> 需求：我们客服团队约 40 人，目前用邮件 + Excel 管理工单，经常漏单、分配不均。想做一个工单系统：客户通过网页和邮件提交工单，系统自动分类分派，客服关单后客户收到通知，主管能看报表。客户数据在第三方 CRM 里，希望工单能关联客户信息。3 个月内上线。

**继续完善——基于已产出的方案迭代**：

> 基于上面的方案，继续跑一轮 pm-requirement-loop，重点检查邮件通道的防漏机制是否闭环。

**指定重点——聚焦某个质量维度**：

> 帮我拆一下这个需求，重点明确各模块与 CRM 系统的接口边界、异常兜底和验收标准。

**补充材料后重新收敛**：

> 这是 CRM 的接口文档，请据此更新之前的待确认问题，继续推进方案。

**跨会话续作**：新会话中把上一轮的「方案状态摘要」粘贴进来，并说明「基于以下状态继续」，Skill 会以该摘要为基线恢复，不会凭记忆臆测旧方案。

使用中的参与方式：澄清阶段它会提出真正影响方案走向的少数问题——你可以回答，也可以不回答（它会按显式标记的假设继续推进，不会替你拍板业务决定）；每轮结束它会给出方案状态摘要，你可随时介入调整方向。

## 6. 输入要求与准备建议

**必需**（缺了无法启动）：

- 一段自然语言的需求描述：想做什么、给谁用、解决什么问题

**建议提供**（直接决定方案质量和评审深度）：

| 材料 | 作用 |
|---|---|
| 业务背景与痛点 | 还原底层目标，避免方案做偏 |
| 目标用户与预期业务结果 | 明确成功判据与验收口径 |
| 现有系统、接口或相关模块的资料 | 避免编造系统能力——没有资料的能力一律标【待确认】 |
| 已知业务规则与约束 | 减少待确认问题数量 |
| 验收要求 / 非功能要求 | 支撑验收标准章节 |
| 既有设计文档、接口文档 | 作为已确认事实的来源依据 |

所有材料缺失时 Skill 仍可运行（资料稀薄场景有专门的降级规则），但未确认内容会以【待确认】或显式假设的形式大量出现在文档中，需后续补充确认。

## 7. 最终输出说明

最终交付**一份**设计文档（不是需求分析、模块设计、功能设计多份割裂交付物），固定 10 章 + 附录结构，围绕一条连续逻辑主线：

| 章 | 内容 | 回答什么 |
|---|---|---|
| 开头 | 方案名称、目标、核心结论（TL;DR）、适用范围、交付状态 | 一眼看懂 |
| 1 | 需求背景、业务问题与目标 | 为什么做 |
| 2 | 总体方案与核心设计决策 | 怎么解决、为什么这么选 |
| 3 | 端到端业务流程与系统交互 | 系统如何协同 |
| 4 | 系统板块划分与职责 | 划成哪几块 |
| 5 | 功能点详细设计 | 每个可开发单元怎么做 |
| 6 | 跨模块契约与关键数据规则 | 模块间靠什么协同 |
| 7 | 依赖关系、风险与关键取舍 | 边界在哪 |
| 8 | 验收标准与测试场景 | 怎么算做完做对 |
| 9 | 交付、部署与运行保障 | 怎么上线、怎么兜底 |
| 10 | 未决问题、假设与风险提示 | 哪些还没定、影响是什么 |
| 附录 | 有效决策清单、已否决方案及理由 | 审计与追溯 |

正文以叙事为主线、表格承载细节，不出现「第 N 轮」等过程性标题，可脱离对话历史独立阅读。全文所有论断带五类标签之一（资料来源 / 用户确认 / 假设 / 建议 /【待确认】），你据此可判断每句话的可信度。

## 8. 质量保障机制

从使用者视角，交付前会强制检查（均为 Skill 规则中实际实现的检查项）：

- **需求覆盖**：每条核心需求有对应设计和验收，无遗漏、无擅自加戏；无需求依据的功能会被删除或移入后续迭代建议
- **逻辑闭环**：核心流程闭环、规则无矛盾、状态流转完整、关键数据有明确的生产者和消费者
- **异常与恢复**：失败、超时、重复请求、部分成功等场景有处理方式或显式标记未决
- **全文一致性**：术语、字段、状态、ID 引用全文一致；验收标准对应的是当前设计而非旧版
- **追溯性**：需求 → 设计 → 功能点 → 验收用例全链路可追溯
- **诚实性**：假设未写成事实、无数值编造、未决问题不被静默丢弃；存在重大未决项时交付「带限制交付」版本并明示限制

**验证状态说明**：以上机制均已在规则文件中实现，并完成过一次端到端测试验证（模拟环境下 2 轮收敛、12 条评审问题被真实发现和修正、最终产出符合 10 章结构的单一文档）。尚未进行多轮真实用户使用验证和新旧版本量化对照测试，实际效果可能因需求类型和资料完整度而异。

## 9. 使用限制与注意事项

1. **输出质量受输入约束**：需求信息不足时，文档中的假设和【待确认】项会较多——这是设计行为（不编造），不是缺陷；补充资料后可继续收敛
2. **系统能力需真实依据**：涉及现有系统的接口、协议、数据模型时，Skill 不会凭"常见工程实践"推断为既有能力；请提供接口文档等资料，否则相关设计只是待验证建议
3. **模型输出仍需人工评审**：生成的设计方案需经业务、架构和研发人员评审后才可进入开发；多轮评审和质量门禁不能替代真实代码验证、接口联调和系统测试
4. **不替用户做业务决定**：属于业务方决策的未决问题会保留其状态并说明影响，不会为了文档显得完整而擅自拍板
5. **不生成工程数值**：性能指标、准确率、响应时间等量化阈值一律标注【待确认】并说明需谁提供口径
6. **一次一个需求主线**：同时引入多个不相关需求时会各自独立开循环，建议分开提交
7. **过程状态存于对话内**：状态默认在当前对话中维护；跨会话续作需粘贴上一轮「方案状态摘要」；如需落盘持久化请明确要求

## 10. 文件结构说明

```text
pm-requirement-loop/
├── SKILL.md                        # 主协议：触发条件、九阶段流程、状态管理、轮次与退出、质量红线
├── README.md                       # 本文件
└── references/
    ├── review-protocol.md          # 反方评审协议：12 评审维度、意见格式、裁决规则、定向修正、回归检查、收敛判定
    ├── document-template.md        # 文档模板：10 章结构、板块八维表、功能点五维表、验收用例表、标注规范
    └── quality-gates.md            # 质量门禁：追溯链规则、六类检查清单、最终 12 条门禁
```

三份 reference 文件由主协议在对应阶段按需加载（不常驻上下文）；与主协议冲突时以 SKILL.md 的核心原则与质量红线为最高约束。

## 11. 常见问题

**Q1：什么样的需求适合使用？**
有明确业务问题要解决、需要产出可指导研发的方案的中等以上复杂度需求（新功能、新系统、流程重构等）。一句话就能答的小问题不建议使用。

**Q2：需求信息不完整怎么办？**
直接开始。Skill 会先识别关键歧义并向你提出真正影响方案的问题；能靠低风险假设推进的部分会显式标注假设后继续。你也可以稍后补充资料，它会基于新信息更新待确认问题并继续收敛。

**Q3：为什么需要多轮评审？**
初稿几乎必然存在流程缺口、规则矛盾和异常场景遗漏。反方评审强制对当前方案找实质缺陷，每条意见带依据和影响分析，经裁决后定向修正——这是设计文档质量的主要保障机制，而非形式流程。若某轮确实没有实质问题，它会直接说明检查结论，不会为凑轮次虚构问题。

**Q4：达到 5 轮上限意味着方案通过了吗？**
不。达到上限只是停止迭代，最终文档会标注「带限制交付」，明确列出未解决的重大问题、影响范围、可开发部分与需等待确认的部分。你可以在明确要求下基于当前方案继续优化，但不会从头重做。

**Q5：为什么最终只生成一份文档，而不是分模块多份交付？**
板块和功能点是同一方案的不同抽象层次，拆成多份独立交付物会造成口径漂移、规则重复和交叉引用断裂。单一文档保证统一的 ID、术语、输入输出和依赖关系，且可脱离对话独立阅读——这正是它相对"各轮分析拼接"的核心优势。

**Q6：如果最终文档仍有重大问题怎么办？**
质量门禁发现重大问题会自动退回修正阶段，而不是硬交。若交付后你发现新问题，把问题反馈给它并要求继续评审轮——它会以当前方案为基线处理，不会推倒重来；属于业务决策的问题会被登记为待确认问题，等待你的决定。
