## 一、文档组织总原则

- **叙事主线为先，结构化表格和图示为辅**：用连续文字解释业务背景、核心机制、流程和设计取舍；用表格表达结构化信息；只在能提高理解效率时使用流程图、时序图或数据流图。
- **章节推导关系**：业务问题决定设计目标 → 设计目标约束核心机制 → 核心机制决定板块职责 → 板块职责拆解为功能点 → 功能点通过数据契约和依赖关系协同 → 验收标准验证是否解决原始业务问题。
- **每章开头**简要说明本章要解决的问题及与上一章的关系；必要时结尾说明本章结论对后续章节的约束。
- **不重复**：已在共享规则章节（第 6 章）完整定义的规则，功能点章节只需引用并说明在当前功能中的应用方式；禁止重复解释同一规则。
- **关键结论**必须说明来源、适用范围和必要的前提条件。
- **分析深度与复杂度和风险匹配**：普通展示功能简洁描述；涉及数据修改、跨系统交互、状态一致性或不可逆操作的功能必须给更充分的规则和异常处理；不要求所有功能点篇幅相同。
- **资料稀薄场景的降级写法**：需求资料只有一段原始描述时，八维/五维表各维度不得缺行、但内容允许简短，来源标注列如实标注「设计」或「建议」；优先压缩篇幅，禁止为填满表格而虚构资料级内容或编造细节。低风险板块的功能点可将五维表合并为紧凑的简表形式，高风险功能点（数据修改、跨系统、不可逆操作）不得降级。
- **交付前检查**：全文逻辑连续性、术语一致性、引用有效性、需求覆盖率和异常闭环（执行 quality-gates.md）。

## 二、最终文档标准结构（10 章 + 附录）

文档开头固定给出：方案名称、方案目标、当前方案的核心结论（TL;DR）、适用范围、当前交付状态及关键限制（正常收敛 / 带限制交付及原因）。随后按以下顺序逐章展开。每章标注「本章回答什么问题」。

### 第 1 章：需求背景、业务问题与目标

说明：需求背景和触发原因；当前业务痛点；目标用户与核心使用场景；表面诉求与底层目标（三层还原表）；预期业务结果；成功判据与验收原则；本期范围与明确不做的内容；已确认约束、设计假设和关键未决问题（含 R-xx 清单）。

**本章回答：为什么要做，具体要解决什么问题。**

### 第 2 章：总体方案与核心设计决策

说明：推荐方案的整体概述；核心机制和工作原理；主要系统职责；关键设计决策（D-xx，含依据、替代方案与取舍）；与现有系统或已有能力的关系；本期方案的主要限制和前置条件。先给结论，再解释原因；不要在尚未介绍核心机制时直接进入大量功能点细节。

**本章回答：准备怎么解决，为什么选择这种方式。**

### 第 3 章：端到端业务流程与系统交互

从用户发起操作开始描述整个业务链路直至最终结果，按实际需求说明：触发条件；关键输入；核心处理步骤；关键校验和决策节点；系统间调用或数据交换；中间状态与结果状态；结果输出与下游消费；主要异常分支；失败后的恢复、重试或人工处理方式。流程图/时序图/数据流图仅在能帮助理解时使用，图中节点、术语和流程必须与正文一致。

**本章回答：整个系统是如何协同工作的。**

### 第 4 章：系统板块划分与职责分析

先给板块总览表，再逐板块用模板一（八维表）展开。板块分析必须解释职责与上下游关系，不能只填抽象描述；复杂板块可先用连续文字解释内部机制，再用表格归纳。

**本章回答：系统划分为哪几块，各块负责什么。**

### 第 5 章：功能点详细设计

先给功能点总览表，再逐个用模板二（五维表）展开。分析深度按复杂度与风险调整（见表达规则）。

**本章回答：每个可开发单元具体怎么做。**

### 第 6 章：跨模块契约与关键数据规则

集中说明跨板块共享的规则，避免在多个功能点中重复定义。按项目实际情况覆盖（只有实际涉及的内容才展开，不机械增加与需求无关的章节）：核心数据实体及关系；关键字段的名称、类型、语义和来源；必填、可选、默认值和约束；字段校验和数据转换规则；上下游数据映射；数据写入、覆盖、更新和存储规则；状态定义与状态迁移；权限与操作确认；接口请求和响应约定；错误处理、超时和重试机制；幂等性与重复请求处理；审计、溯源与操作记录；数据一致性和失败恢复要求。

**本章回答：模块之间靠什么规则协同。**

### 第 7 章：依赖关系、风险与关键取舍

集中展示：核心板块和功能点的依赖关系（可用依赖图，图与 ID、正文一致）；关键数据流转路径；重要的外部系统依赖；尚未验证的工程前提；关键设计取舍；主要风险及缓释措施；失败时的处理和恢复责任；本期方案的限制。

**本章回答：方案的依赖与风险边界在哪。**

### 第 8 章：验收标准与测试场景

用模板三（验收用例表）组织，验收标准必须可观察、可执行、可判定。不得编造准确率、响应时间、吞吐量等量化指标；需要时标【待确认】并说明需业务或工程团队提供的目标与测量口径。

**本章回答：怎么判定做完了、做对了。**

### 第 9 章：交付、部署与运行保障

按实际交付场景说明：环境与系统依赖；配置要求；部署和启用步骤；与现有系统的集成要求；联调责任与验证方式；上线检查；监控、日志和问题排查要求；回滚、降级和恢复策略。资料未覆盖的部署能力和运行机制不得擅自认定为现有能力。

**本章回答：怎么上线、怎么兜底。**

### 第 10 章：未决问题、假设与风险提示

集中列出：尚未确认的业务规则（Q-xx）；尚未验证的系统能力；需进一步明确的接口或数据契约；会影响开发范围的关键假设；仍未完全解决的重大问题；可能导致方案调整的外部依赖。每项说明影响范围、默认假设、确认责任或建议的验证方式。本章不能掩盖前面章节的缺陷——关键问题应在对应正文明确标记，并在本章汇总。

**本章回答：哪些事还没定，影响是什么。**

### 附录：决策与变更记录

仅保留对理解当前方案、审计决策或后续维护有实际价值的记录：当前有效决策（D-xx）清单、已否决方案及理由、（如有必要）每轮循环的一句话摘要。不得把所有轮次的完整分析过程附加进最终文档。

## 三、模板一：板块拆解八维表

先给板块总览表（放在所有板块表之前）：

| 板块 ID | 板块名称 | 核心职责（一句话） | 上游依赖 | 下游消费方 | 优先级 | 主要风险 |
|---|---|---|---|---|---|---|

再逐板块展开：

### 板块 M-xx：{板块名称}

| 维度 | 内容 | 来源标注 |
|---|---|---|
| **职责** | 该板块解决什么问题、不解决什么问题（边界写清楚） | |
| **输入** | 数据来源、格式、触发方式、前置条件（字段级，至少关键字段） | |
| **颗粒度** | 板块内部处理单元细化到什么程度（如：到字段 / 到条记录 / 到单据） | |
| **输出** | 产出物、格式、写入目标、下游消费方 | |
| **核心规则** | 判定逻辑、状态流转、优先级、冲突处理规则 | |
| **可信保障** | 如何让输出可被信任：校验机制、溯源、人工确认关口、准确率指标及口径 | |
| **预期效果** | 对用户/业务的可感知价值，可量化优先 | |
| **边界异常** | 输入缺失/格式错误/上游失败/超时/数据冲突时的行为与兜底（**禁止填"无"**） | |

## 四、模板二：功能点五维表

先给功能点总览表（放在所有功能点表之前）：

| 功能点 ID | 名称 | 归属板块 | 服务的需求 ID | 上游依赖 | 下游影响 | 优先级 | 风险等级 |
|---|---|---|---|---|---|---|---|

再逐功能点展开：

### 功能点 F-xx：{名称}（归属：板块 M-xx）

| 维度 | 内容 |
|---|---|
| **目标与效果** | 要解决什么问题；用户可感知的结果；触发条件；验收判据（可测试，关联 AC-xx） |
| **核心规则与逻辑** | 输入条件、判定规则、算法/流程、状态流转、异常分支；规则冲突时的优先级 |
| **支撑设计方案** | 依赖的板块、现有系统能力、关键数据、接口契约（同步/异步、协议、频率）；尚未验证的接口能力必须标【待确认】或「建议」 |
| **实现方式** | 推荐实现路径、关键技术取舍（为什么这么选、放弃了什么）、可复用能力、工作量分级（S/M/L，资料不足时不虚构精确工作量）与优先级 P0/P1/P2 |
| **预判问题与应对** | 该功能点特有的风险、失败模式、降级/回滚方案、恢复策略（**禁止填"无"**，想不清标【待确认】） |

## 五、模板三：验收标准用例表

每个用例一行，关联到需求或功能点 ID：

| 用例 ID | 关联需求/功能点 | 前置条件 | 输入或操作 | 预期结果 | 异常验证 |
|---|---|---|---|---|---|

根据功能实际情况覆盖以下场景（只有相关的才纳入）：正常流程；边界输入；缺失或非法数据；权限不足；依赖系统失败；超时与重复操作；部分成功；数据一致性；用户取消；恢复与重新执行。

## 六、标注规范与示例

### 五类信息标签

| 写法 | 含义 |
|---|---|
| 「报告解析需抽取 5 类约 20 个字段」（来源：N-1.1） | 已确认事实——资料原文，保留来源标签（如 `P`/`S`/`N`/`R` 或文件名缩写） |
| 「用户确认按 X 口径处理」（用户确认，2026-xx-xx） | 已确认事实——用户明确确认（仅在用户实际作出确认时使用；用户从未确认任何内容时，「已确认事实」仅限资料原文支持的内容，不得用此标签） | |
| 「假设现有 CRM 提供 API（原因：资料未说明；影响：F-03 分派逻辑；验证：技术验证）」 | 设计假设——显式标注四要素 |
| 「建议采用 harness 承载主循环」（建议） | 设计建议——本文设计推演，资料无直接依据 |
| 「风险点字段口径【待确认】（影响 F-05）」 | 未决问题——资料未覆盖或自相矛盾 |
| 「已否决：纯规则引擎方案（原因：无法覆盖长尾 case，见 D-03）」 | 已否决方案——保留理由，不进入方案主体 |

规则：资料结论与建议在同一张表中出现时必须分别标注；不得把建议写成祈使句伪装成需求；不得把假设写成确定事实。

## 七、表达规则

### 什么时候用连续文字

解释业务问题、核心机制、关键流程、设计取舍、复杂规则组合、重要系统协作关系时，用连续文字叙事。让未参与前期讨论的研发人员能独立理解当前方案。

### 什么时候用表格

板块和功能点总览、字段定义、规则对比、依赖关系、问题清单、验收标准——结构化、可枚举、需要逐项核对的内容。

### 什么时候用图示

端到端流程、复杂状态迁移、系统时序、跨模块数据流——且仅当图确实比文字更易理解时。图中节点、术语必须与正文一致。

### 禁止事项

- 不得为满足格式要求把所有内容机械转成表格
- 不得使用空泛表述（"提高效率""保证可靠性""完善异常处理"）而不说明具体机制
- 不得重复解释同一规则
- 不得用不同术语描述同一对象而不作定义
- 不得让功能点列表脱离总体方案独立存在
- 不得在正文出现「第 N 轮」等过程性标题（轮次记录只进附录）
