## 一、评审视角要求

评审者与方案设计者是同一模型的不同视角，切换必须彻底：

- **不得复述方案**：复述不是评审。
- **不得默认方案正确**：每个关键机制都要主动找反例。
- **不得为反驳而反驳**：不得为了证明自己完成了评审任务而刻意否定合理设计。评审必须基于当前方案及已有资料提出可验证的缺陷。

## 二、12 个评审维度

每个维度至少主动检查一次，无问题时记录"已检查、未发现问题"的结论，不需要虚构问题：

| # | 维度 | 检查什么 |
|---|---|---|
| 1 | 目标有效性 | 方案是否真正解决底层业务问题，是否存在偏离目标的设计 |
| 2 | 需求覆盖性 | 是否遗漏明确要求，是否擅自引入未授权的功能 |
| 3 | 业务逻辑正确性 | 规则之间是否矛盾，状态流转是否合理 |
| 4 | 用户操作完整性 | 用户从开始到结束是否存在无法继续、无法取消或无法理解的环节 |
| 5 | 技术可行性 | 是否依赖尚未确认的接口、数据或系统能力 |
| 6 | 数据完整性 | 关键数据是否有明确来源、类型、校验、存储和消费方 |
| 7 | 跨模块一致性 | 上下游字段、状态、错误处理和职责是否一致 |
| 8 | 异常与恢复能力 | 失败、超时、重复请求、数据冲突和部分成功时如何处理 |
| 9 | 安全与权限边界 | 涉及数据修改时，是否明确权限、确认、审计和失败保护要求 |
| 10 | 验收可执行性 | 是否存在无法测试、无法判定或缺少预期结果的验收条件 |
| 11 | 复杂度合理性 | 是否存在可以用更简单机制解决的问题 |
| 12 | 交付可行性 | 部署、配置、联调、回滚和运维是否存在未被识别的依赖 |

## 三、评审意见标准格式（I-xx）

每条有实际价值的评审意见完整记录以下字段（首次提出时全量给出，后续轮次只更新状态相关字段）：

| 字段 | 内容 |
|---|---|
| 问题 ID | 稳定编号 I-01、I-02…，全程不复用 |
| 关联对象 | 受影响的 R-xx / D-xx / M-xx / F-xx / Q-xx |
| 问题描述 | 明确指出当前设计的具体缺陷 |
| 成立依据 | 规则矛盾、资料证据、反例或具体业务场景——必须是可验证的 |
| 影响分析 | 对业务、数据、用户操作或交付的实际影响 |
| 严重程度 | 重大 / 一般 / 低影响（分级标准见下节） |
| 建议处理方式 | 具体可执行的修正方向 |
| 裁决状态 | 待裁决 / 已接受 / 已拒绝 / 待确认 / 已关闭 |
| 修正结果与回归检查 | 接受后记录实际变更内容及检查了哪些关联对象 |

问题状态机：待评审 → 待裁决 →（已接受 → 已修正 → 已关闭 ｜ 已拒绝 → 已关闭 ｜ 待确认）。已关闭的问题不得重复提出，除非出现新证据证明原裁决有误（此时标记为已重新打开）。不得通过删除问题制造"没有未解决问题"的假象。

## 四、严重程度分级

按实际影响判断，不得为了追求严格把所有问题都判为重大缺陷：

- **重大缺陷**：可能导致核心业务目标无法实现、关键流程不闭环、数据错误或不一致、未经授权的修改、关键依赖不可行，或核心验收无法完成。
- **一般缺陷**：影响部分场景、模块衔接、可维护性或交付效率，但不必然导致核心流程失败。
- **低影响优化**：不影响核心正确性与交付的体验改进、文案优化或非必要的架构改进。

## 五、裁决规则

对每条 I-xx 意见作出裁决，裁决必须给理由：

### 接受

问题成立且需要修正时接受。修正必须定位到具体设计对象：哪项规则需要调整、哪个板块或功能点需要更新、哪些输入输出或接口契约需要同步、哪些异常流程需要补充、哪些验收条件需要修改。

### 拒绝

以下情形可拒绝，必须说明拒绝理由及适用前提，不能只写"无需修改"：

- 评审意见缺乏充分依据（无法给出规则矛盾、资料证据或具体反例）
- 与已确认需求（R-xx）冲突
- 成本明显超过收益（此时考虑降级为低影响优化或后续迭代建议）

### 待确认

裁决依赖用户决策、业务资料或真实工程能力时标记待确认：

- 可在合理假设下继续 → 继续设计并显式记录假设
- 不同答案会导致核心方案实质性分歧 → 暂停受影响的设计部分，作为 Q-xx 向用户澄清

## 六、决策记录规范（D-xx）

阶段 C 及后续各阶段产生的关键决策按此格式记录（每条决策首次创建时全量给出）：

| 字段 | 内容 |
|---|---|
| 决策 ID | D-01、D-02…，稳定不复用 |
| 决策内容 | 一句话说明决定了什么 |
| 决策依据 | 支撑决策的 R-xx、资料来源或分析结论 |
| 替代方案 | 被考虑过的其他方案（没有实质分歧时可写"无实质分歧"） |
| 选择理由 | 为什么选当前方案 |
| 代价与风险 | 当前方案的主要代价 |
| 当前状态 | 有效 / 已废弃（废弃时注明替代决策 ID） |
| 关联对象 | 受影响的 R-xx / M-xx / F-xx |

已被替换的决策标记为已废弃并记录替代决策，不得让两个相互冲突的决策同时作为当前有效方案出现。

## 七、定向修正规则

- **只改受影响部分**：每轮只修改受到问题影响的部分，不得无理由重写整个方案。
- **修正后同步更新**：当前方案基线、相关板块和功能点、关键流程与数据流、决策记录、相关验收标准、问题状态和关联关系。
- **旧方案处置**：被替换的设计必须明确状态（已废弃 / 已被 D-xx 替代），旧内容不得继续以有效结论的形式出现在最终文档中。
- **禁重复分析**：已关闭的 Q-xx / I-xx 不得在后续轮次重复提出；不为展示迭代而重新分析已关闭的问题。

## 八、全局一致性与回归检查

每次定向修正后，检查以下 12 项（发现问题的更新对应对象并做必要的局部回归）：

1. 是否出现前后矛盾的业务规则
2. 是否同一术语指代不同概念
3. 是否同一状态在不同章节使用不同定义
4. 是否出现功能点 ID、需求 ID 或问题 ID 引用失效
5. 是否上下游字段名称、类型或语义不一致
6. 是否流程图与文字描述不一致
7. 是否输出已改变但下游消费逻辑未同步
8. 是否异常处理与正常流程相互矛盾
9. 是否验收条件仍对应旧版设计
10. 是否引入超出需求范围的新功能
11. 是否删除了仍被其他功能依赖的能力
12. 是否存在设计声称具备、但没有资料证明的现有系统能力

只有当修改影响范围较大、存在多个关联矛盾或核心机制发生变化时，才重新检查整个方案。

## 九、收敛判定

每轮评审结束后，以下条件**全部满足**才判定收敛：

- 核心业务目标和本期范围明确
- 核心业务流程完整
- 核心机制能够解释主要业务行为
- 板块职责和功能点边界合理
- 关键输入输出和上下游依赖明确，或已标记待确认
- 不存在尚未处理的重大设计缺陷
- 关键异常场景有明确处理方式，或已明确说明其未决状态
- 需求、设计、功能点与验收标准之间可追溯
- 全局一致性检查通过
- 当前没有值得继续修正的重大问题

处理规则：

- 仍有重大缺陷 → 进入下一轮定向修正
- **收敛判定的时机**：本轮发现的重大问题已完成修正且回归检查通过后，当轮即可对照以下十项条件判定收敛，不强制空跑一轮复核；但若本轮修正触及核心机制（阶段 C 层面的方案变更），下一轮须至少复核受影响的评审维度
- 只剩低影响优化项 → 不为消除所有可想象的问题而无限迭代，直接收敛
- 有未决问题但可基于明确假设推进 → 形成附带假设的方案交付，未验证前提不得写成确定事实
- 收敛判定结论写入当轮「方案状态摘要」

## 十、最大轮次与异常退出

- 实质性评审与修正最多 **5 轮**；需求澄清交互不计入，但不得通过拆分形式轮次规避上限。
- 达到轮次上限时：
  1. 立即停止常规迭代
  2. 整理当前最佳方案（仍以 Design Baseline 为准）
  3. 标记尚未解决的重大问题及其影响范围
  4. 区分可以继续开发的部分与必须等待确认的部分
  5. **不得将达上限等同于方案通过评审**——最终文档需注明"带限制交付"及具体限制
- 用户明确要求继续优化的，以当前有效基线继续，不从头重做。
