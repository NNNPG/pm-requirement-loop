## 一、追溯链规则（Traceability Map）

维护以下关联链，是需求覆盖检查与验收追溯的基础：

**需求 R-xx → 设计决策 D-xx / 核心机制 → 板块 M-xx → 功能点 F-xx → 验收用例 AC-xx**

规则：

- 每个核心需求至少关联到相应的设计内容，或明确说明暂不实现的原因
- 每个核心功能点应能追溯到其服务的需求或必要的系统约束
- 每项关键验收标准应能追溯到对应需求或设计规则
- 功能点没有需求依据时：检查它是否属于必要的支撑机制；若不是，删除或移入后续迭代建议
- 需求没有对应设计或验收内容时：视为覆盖缺口，必须补齐或显式说明

## 二、需求覆盖检查

- [ ] 所有已确认的核心需求（R-xx）有对应设计
- [ ] 所有核心需求能关联到相关板块和功能点
- [ ] 不存在没有需求依据的功能（或已标注为支撑机制/后续迭代建议）
- [ ] 没有明确要求被遗漏或错误改写
- [ ] 本期范围与非目标（明确不做的内容）清晰
- [ ] 用户确认过的约束被完整保留

## 三、方案逻辑检查

- [ ] 核心业务流程闭环
- [ ] 各板块职责明确、无无法解释的重叠
- [ ] 各功能点有合理的上下游关系
- [ ] 核心规则无矛盾
- [ ] 状态流转完整
- [ ] 关键数据能正确传递（生产者 → 消费者链路闭合）
- [ ] 关键失败场景有明确处理方式或显式未决标记
- [ ] 无不必要的复杂设计（能用更简单机制解决的未遗留复杂方案）
- [ ] 关键实现不依赖未经验证且未标记的系统能力

## 四、全文一致性检查

- [ ] 术语全文统一（同一对象同一称呼）
- [ ] R / Q / D / M / F / I / AC 所有 ID 引用有效（无悬空引用、无失效编号）
- [ ] 相同字段有相同语义和类型
- [ ] 相同状态有相同定义
- [ ] 总体流程与功能点细节一致
- [ ] 接口契约与上下游使用方式一致
- [ ] 验收标准对应当前有效设计（不对应旧版设计）
- [ ] 无残留已废弃方案、旧规则或重复内容

## 五、工程可执行性检查

- [ ] 关键功能有明确输入、输出和处理逻辑
- [ ] 重要规则可转化为代码或配置
- [ ] 依赖系统和接口有明确责任边界
- [ ] 异常行为可预期
- [ ] 数据修改有适当的权限、确认和审计要求
- [ ] 失败恢复和重复操作有合理处理方式
- [ ] 开发人员能据此判断功能完成与否
- [ ] 仍需确认的工程前提明确标注（无暗中假设）

## 六、可读性检查

- [ ] 读者能快速理解为什么做、总体怎么做（TL;DR + 第 1、2 章达标）
- [ ] 各章节按业务逻辑自然递进（推导关系成立，无脱节的表格堆砌）
- [ ] 无大量重复背景和泛化风险提示
- [ ] 无为填充模板而生成的低价值内容
- [ ] 无缺少解释的功能清单（每个功能点都挂在方案主线下）
- [ ] 图表真正提高理解效率（与正文一致）
- [ ] 重要设计取舍有理由
- [ ] 文档可脱离 Loop 对话历史独立阅读

## 七、来源与事实检查

- [ ] 资料事实与设计建议明确区分（标签齐全）
- [ ] 用户尚未确认的假设未被写成确定结论
- [ ] 现有系统能力有真实依据（无编造的接口、字段、业务规则）
- [ ] 无未经支持的数值、性能指标或验收阈值
- [ ] 未决问题被完整保留（未被静默丢弃或删除）
- [ ] 无为使文档看起来完整而编造的内容

## 八、最终质量门禁（12 条）

最终文档必须同时满足以下条件，缺一即返回修正：

1. 核心业务目标清晰
2. 推荐方案及关键取舍明确
3. 端到端流程能够被理解
4. 板块与功能点层次一致
5. 关键数据和系统契约明确，或明确标记待确认
6. 核心异常场景有处理方案，或明确说明尚未解决的风险
7. 需求与验收标准之间可追溯
8. 全文术语、规则和 ID 一致
9. 资料、建议、假设与未决项可以区分
10. 不存在尚未处理且被隐瞒的重大缺陷
11. 文档可以脱离对话历史独立阅读
12. 不存在明显的重复堆砌和无意义的格式填充

## 九、检查结果处理

- **发现重大问题**：返回阶段 F，针对受影响部分修改并重新执行相关检查，不重做整个 Loop。
- **只存在一般优化项**：在不影响核心正确性的前提下保留并记录，不阻塞交付。
- **仍有未决问题但可在明确假设下推进**：交付带风险说明和待确认清单的版本。
- **关键前提未定且不同答案会导致完全不同的方案**：不得将该方案描述为已完全定稿，必须注明"带限制交付"及限制内容（例如达到轮次上限仍未收敛的情形）。
